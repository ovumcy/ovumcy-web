### Fixed

- **The example stacks now forward every setting the app reads.** The five stacks under `docs/examples/` listed their environment by hand and left out `REGISTRATION_MODE`, `HSTS_ENABLED`, `AUDIT_LOG_ENABLED`, `WEBHOOK_BLOCK_PRIVATE_ADDRESSES`, `REMINDER_SCHEDULER_ENABLED`/`REMINDER_SCHEDULER_HOUR` and the register, logout and calendar rate limits, so a value set in `.env` for any of them changed nothing and a public proxy stack ran with open registration whatever the runbook advised. Each is now passed through with the application's own default, so a stack started as before behaves as before. A repository test type-checks the binary, finds every environment variable it reads by following the name to `os.Getenv`, and fails when an example omits one, or fixes it to a literal that ignores `.env`, without a stated reason. The runbook names the few settings a stack fixes on purpose, and now says to create accounts under `REGISTRATION_MODE=closed` with `ovumcy users create`.
- **The upgrade steps and the downgrade caveats no longer overpromise.** The runbook and the README now say to take the new compose file, or add the `ovumcy_fence` volume, before the first v2.0.0 start: without it every armed calendar feed is disarmed on every start. The downgrade section gains the case a release older than v2.0.0 can reopen: a feed revoked under it is brought back by restoring an earlier backup under the same fence file, and the remedy is `docker compose down` followed by removing the `ovumcy_fence` volume before upgrading again. The statement that a restore cannot revive a revoked feed now says which revocations the fence sees, in the runbook, the data-protection note and both security documents. The statements that a pre-041 binary refuses to start and that migrations 032/034/035 need nothing in either direction are corrected.
