# Known Information Disclosure

_Part of the [Ovumcy security policy](../../SECURITY.md)._

## Known Information Disclosure

A few information-disclosure signals are accepted residual risk because closing them either breaks core flows or requires infrastructure Ovumcy does not assume self-hosters have (for example SMTP).

### Register enumeration: pickup-cookie follow-up oracle (residual)

`POST /api/v1/users` returns identical status, body, and Set-Cookie shape (a single sealed `ovumcy_register_pickup` cookie of fixed length, no `ovumcy_auth` or `ovumcy_recovery_code`) for both a brand-new email and a duplicate. Response timing is also equalized: the duplicate-email branch runs `equalizeRegistrationTiming` (two bcrypt comparisons at `passwordHashCost` — cost 12, the same cost the placeholders embed and a test pins) to match the work `BuildOwnerUserWithRecovery` performs on the new-email branch (password hash + recovery-code hash), so the single POST response carries no observable difference. The follow-up `GET /register/welcome` then dispatches the pickup cookie either to `/register` (with auth and recovery cookies) for a valid pickup or to `/login` (with a neutral flash) for a decoy or expired pickup. An attacker who holds their own pickup cookie from a probe POST can therefore observe which redirect target their cookie resolves to and infer whether the email was new or already registered. This turns the single-request status / cookie / timing oracle into a two-request probe whose rate the per-IP budget on `POST /api/v1/users` bounds transitively: the follow-up `GET /register/welcome` carries no limiter of its own, but each observation consumes a single-use pickup nonce mintable only through that rate-limited POST, and the login bcrypt-timing equalization (`equalizeAuthCredentialsTiming`) further bounds any cross-endpoint follow-up.

Closing the residual signal entirely is mathematically impossible without an out-of-band verification channel: any in-app dispatch on the pickup cookie reveals the branch, and any login-after-register variant turns the probe into a follow-up `POST /api/v1/sessions` whose success or failure carries the same information. The only options are (a) a magic-link / email-driven enrollment that gates registration behind SMTP delivery (not assumed in the self-hosted deployment model), or (b) acceptance of the documented two-request probe. Both are revisited if Ovumcy ever ships a multi-tenant SaaS variant.

A separate vector — replay of a sealed `ovumcy_register_pickup` cookie captured from somebody else's response within the 5-minute TTL — is **not** part of this residual. The pickup cookie carries an opaque nonce that is consumed atomically through `register_pickup_tokens` on the first `GET /register/welcome` call; a captured cookie reaching the welcome endpoint a second time gets the same neutral `/login` redirect as a decoy or expired pickup, and cannot mint a second `ovumcy_auth` session.

### Login: `requires_totp` reveals 2FA status (accepted design decision)

`POST /api/v1/sessions` returns `{"requires_totp": true}` when the supplied password is correct and the account has TOTP enabled, and `{"ok": true}` plus a session cookie otherwise. A credential-dump attacker can use this to triage accounts by whether they have a second factor.

This is inherent to any password-then-TOTP flow that gates the second factor on account state — any uniform response that hides the difference either silently grants access without verifying TOTP (downgrade attack) or unconditionally rejects accounts without TOTP (lockout). The per-account rate limiter (`AuthAttemptPolicy`) and the recovery-code re-auth requirements bound the value of knowing the 2FA status.

### Auth sessions: absolute expiry only, no idle timeout (accepted design decision)

`ovumcy_auth` is bounded by an absolute TTL — 7 days by default, 30 days with remember-me — and carries no separate idle/inactivity timeout: a session that is used once and then left untouched remains valid until the absolute TTL elapses, not until some shorter period of inactivity. This widens the exposure window for a cookie captured early in its lifetime compared to a design with a sliding idle timeout.

The trade-off is deliberate rather than an oversight. Exposure is bounded two ways instead of one: the absolute TTL caps how long any captured cookie stays valid regardless of activity, and every request re-verifies `users.auth_session_version`, so any credential or posture change (password change/reset, recovery-code regeneration, forced operator reset, TOTP enable/disable, clear-data) revokes the cookie instantly rather than waiting for it to expire. For a personal, self-hosted health tracker — not a shared-workstation enterprise product — an idle timeout mainly adds friction (repeated re-logins) without a correspondingly large security gain, since the operator is typically also the sole user. This is not test-enforced; it is reviewed as a design decision, and revisited if the deployment model changes (see [Threat Model](threat-model.md)).

### Password reset issues a session without a second-factor challenge (accepted design decision)

Two paths mint an `ovumcy_auth` cookie without ever consulting the account's second factor, and both leave through the same door: `POST /api/v1/password-resets/redeem` goes from `CompleteReset` straight to `setAuthCookie` with no TOTP step in between (`internal/api/handlers_auth_session_recovery.go`), so on both of them the factor is skipped rather than deferred. They rest on different reasoning and are stated separately rather than collapsed into one sentence.

**The operator-forced reset.** `LoginService.Authenticate` (`internal/services/login_service.go`) consults `TOTPEnabled` only on the branch where `MustChangePassword` is false. An account an operator has flagged for a forced change — the CLI `ovumcy reset-password <email>` — is therefore issued a reset token and routed to `/reset-password` on the correct password alone, even when TOTP is enabled on it, and the session handed over at the end of that reset was never gated on the second factor.

That precedence is a standing decision, not an oversight, and the reasons it is left alone are load-bearing. `users.totp_secret` is encrypted under a key derived from `SECRET_KEY`, so after a rotation the stored ciphertext no longer opens and no code the authenticator produces can satisfy the challenge; `docs/security/cryptography.md` (*Operational caveat — rotating `SECRET_KEY` with 2FA accounts*) and `docs/self-hosted.md` both send exactly that owner down the operator-reset route. Letting TOTP win here would withdraw the escape hatch from precisely the accounts whose second factor is already unusable, leaving permanent owner lockout with no in-product remedy. It would also break a published claim somewhere else entirely: `internal/api/handlers_auth_oidc_link_confirm.go` branches on `RequiresPasswordReset` and carries no arm for a login result that asks for a TOTP challenge instead, so a both-flags target that stopped raising the reset flag would fall through to `setAuthCookie` and receive a session where `SECURITY.md` (*OIDC Account Linking*) states it is routed to `/reset-password`. Link-confirm verifies TOTP in its own right before either branch, so what a reversal would silently drop on that path is the forced-reset routing, not the factor.

What the skip does not touch is the first factor or containment. The forced reset still requires the account's correct current password *and* an operator-set `must_change_password`; it is a skip of the second factor only, and it is the one sanctioned exception to the rule that every session-issuing route verifies as many factors as ordinary sign-in. For a TOTP-enabled account this route costs one secret where sign-in costs two; what bounds the exception is that it opens only after an operator has set `must_change_password` out of band, never on anything the account holder or an attacker can reach. And the write that completes a reset bumps `auth_session_version` in the same `Updates()` that rewrites the password hash (`UpdatePasswordRecoveryCodeAndRevokeSessionsCAS`, `internal/db/user_repository.go`), as does the operator's own write (`ForceResetPasswordAndRevokeSessions`), so every session predating the reset is revoked in the same statement. Unlike the other entries in this file, this one is test-enforced: `TestLoginServiceForcedResetOutranksTOTPForAnAccountWithBothFlags` in `internal/services/login_service_test.go` pins the ordering at the service, `TestLogin_ForcedResetOutranksTOTP_RoutesToResetAndIssuesNoAuthCookie` in `internal/api/auth_login_totp_required_regression_test.go` and `TestCompleteOIDCLinkConfirmationRoutesAForcedResetTOTPTargetToResetWithoutASession` in `internal/api/auth_oidc_regressions_test.go` pin it at both callers. A failure in any of the three means the decision was reversed, not that the assertion went stale.

**The recovery-code reset.** `POST /api/v1/password-resets` resolves the account from its email, its recovery code *and* its password (`StartRecovery`, `internal/services/password_reset_service.go`) and mints the reset token; redeeming that token rewrites the password and issues the session, again with no TOTP step anywhere on the path. This is intended design rather than a residual gap: the recovery code stands in for the **second** factor and never for the first, so the route costs two secrets — the same count the ordinary sign-in path charges a TOTP-enabled account — and holding the code alone buys nothing. `docs/SECURITY_INVARIANTS.md` (*Authentication and sessions* → *Password recovery takes two factors, not one*) states that shape and the cost that comes with it; gating the route on a TOTP **code** instead was rejected for the same lockout reason as above, since the owner it exists for is the one whose second factor just stopped working.

One durability property bounds the claim and is stated here rather than left to be re-derived. A recovery code survives routine password changes: `SettingsService.ChangePassword` (`internal/services/settings_password_policy.go`) writes through `UpdatePasswordAndRevokeSessions` (`internal/db/user_repository.go`), which does not touch `recovery_code_hash`. So a code issued at registration stays live no matter how often the password is changed afterwards, until it is redeemed — the reset write rotates `recovery_code_hash` in the same statement — or regenerated from Settings, which invalidates it immediately and bumps `auth_session_version` with it. A code that leaked and was never regenerated therefore remains one of the two secrets this route asks for. That is ordinary backup-code behaviour, and it is what a reader needs in order to size the exposure.

### Rate-limit and attempt-limiter state: process-local, resets on restart (accepted design decision)

Per-IP HTTP rate limits (Fiber's limiter middleware) and the per-account `AttemptLimiter` budgets (`internal/services/attempt_limiter.go`) are held in the process's own memory. They are correct only under the single-instance self-hosted deployment this codebase assumes: state is not shared across replicas, and a process restart silently resets every counter and cooldown.

This is a deliberate scoping choice, not a gap discovered after the fact: sharing limiter state across processes would require an external store (Redis or similar) that Ovumcy does not assume a self-hoster has provisioned, and the baseline deployment path is explicitly single-instance (see *Deployment* in `docs/SECURITY_INVARIANTS.md`). Anyone horizontally scaling Ovumcy behind a load balancer must be aware that each replica enforces its own independent budget — running N replicas multiplies the effective per-IP and per-account attempt budget by N — and should either keep the deployment single-instance or introduce a shared limiter store before scaling out. This is not test-enforced; it is a documented operational constraint of the current architecture.

### Login rate limiting: address-keyed budget can lock out a shared address (accepted design decision)

The login budget (`AuthAttemptPolicy`, `internal/services/auth_attempt_policy.go`) checks two buckets and blocks once *either* one fills (`TooManyRecentAny`): an identity bucket derived from the submitted email, and a client bucket keyed on the bare client address alone (`login:client:<addr>`). `LoginService.Authenticate` (`internal/services/login_service.go`) passes the client address into that client bucket unmodified, with no account information folded in. Eight failed attempts within 15 minutes from one address exhausts that bucket regardless of which account each attempt targeted, so on a household instance where several independent owners share one NAT address, one owner mistyping their password — or an attacker spraying guesses across several accounts from that address — locks every owner behind it out of login for the remainder of the window.

This is the opposite keying choice from the settings re-auth budget, and deliberately so: `docs/security/auth-policy-and-rate-limits.md` (*Rate Limits*) explains why the re-auth budget is keyed on `(client, account)` and on the account alone, never on the address by itself — re-auth is reachable only with a session for one specific account already in hand, so an address-wide bucket would buy no protection there while still locking out co-tenants. Login is reachable with no session at all, and an attacker can spray password guesses across many accounts from a single address without ever tripping any one account's identity bucket; the address-keyed client bucket is what catches that spray. Dropping it in favor of pure per-account keying would remove the shared-NAT lockout at the cost of letting an address-spraying attacker guess indefinitely as long as it keeps rotating target accounts — the more dangerous failure mode against login specifically, which re-auth does not share. This is not test-enforced; it is reviewed as a design decision.

### Calendar-feed polling is not audited (accepted design decision)

The audit stream records the moment the `.ics` subscribe URL is revealed to the owner (`action="settings.calendar_feed_reveal"`, `domain="health_egress"`), and records nothing at all for the requests that later fetch the feed at `GET /calendar/feed/:token.ics`. The other surfaces that carry an owner's health data out of the instance — the CSV, JSON and summary exports — are audited under the same domain; in-app page reads (dashboard, calendar, stats, the day views) are not audited at all, by the same read-side boundary. The feed sits between the two — an egress capability whose polls look like page reads — so the omission is stated here rather than left to be re-discovered as a gap.

Decision (2026-07-28): the audited unit for this capability is the reveal, not the poll. Three reasons, and each holds on its own. Calendar clients re-fetch a subscribed feed on their own schedule — hourly is typical, and several subscribed devices multiply it — so auditing the poll would bury every deliberate action in the stream under an unbounded volume of routine traffic generated by nobody. The route is also the one endpoint reached without a session: it resolves a bearer capability token and deliberately answers `404` with no oracle, so a line naming the resolved owner would publish, in the log, the association the endpoint is built not to confirm — and a line recording each refusal would turn the log itself into the enumeration oracle the route avoids. Finally, the reveal already carries the information an incident review needs from this surface: a feed is a standing capability, so *when was a subscribe URL handed out, and to which account* is the question that distinguishes one instance's exposure from another's, while *how often did a calendar client fetch it* does not.

What is lost is the ability to see, from the audit stream alone, that a leaked subscribe URL was being used. Two other controls cover that ground: the Fiber request log (always on, independent of `AUDIT_LOG_ENABLED`) records every feed request with its sanitized path, and a token suspected of leaking is rotated or revoked from Settings, which invalidates it immediately. This is not test-enforced; it is reviewed as a design decision, and revisited if the feed ever serves more than the owner's own predicted cycle events.

### Coercion: no duress mode, and a decoy account is only credible as the first one (accepted design decision)

Ovumcy has no duress mode: there is no second password that opens an empty profile, no hidden entries, and no reversible erasure. The closest thing the product offers is `Settings → Clear data`, which the codebase treats as a deliberate "panic clear" — in one transaction it deletes the day record and every owner-created symptom, resets the cycle, tracking and reminder preferences (and the stored timezone) to their defaults, disarms the webhook, revokes the calendar feed, and bumps `auth_session_version` so every other signed-in device loses its session at the same moment. What survives is the account itself: the email, display name, interface language, local password, a TOTP enrollment, an OIDC link and the onboarding-complete flag are deliberately untouched (pinned by `TestClearDataPreservesAccountIdentityFields`). What is left is therefore not distinguishable through the interface from an account that was created, onboarded and configured the same way but never used for tracking: the tracked record is gone, the built-in symptom catalogue and every tracking preference read their defaults, and no surface anywhere renders the account's creation date — but the wiped account keeps whatever identity and auth posture it had, so it reads as configured-but-unused rather than freshly registered. The erasure is final in-app, though. The only way back is a JSON export taken beforehand and re-imported afterwards, which restores the day-level record and nothing else — cycle and tracking settings, the stored timezone, the webhook endpoint, the calendar feed, and any custom symptom that was never logged on a day all sit outside the export by design (see [`docs/gdpr.md`](../gdpr.md)).

A second, decoy account is invisible through the interface: no surface renders an account count, and `SetupService.RequiresInitialSetup` only ever answers whether the instance has *zero* accounts, on the unauthenticated login and register pages. It is not invisible through the API. Ovumcy uses ordinary sequential primary keys, and two independent responses expose where an account sits in that sequence — `GET /api/v1/users/current` returns the owner's own `id`, and the per-owner built-in symptom catalogue draws its ids from the same table-wide sequence, so a second owner's sixteen built-ins are numbered from wherever the previous owner's rows ended rather than from 1. Either one tells whoever is looking at the screen that this is not the first account on the instance, so a decoy is only credible when it is the account that was created first.

Suppressing one of those identifiers would not close the signal, and closing it properly is a larger change than it looks: the symptom ids are the resource identifiers the API needs for update, restore, and per-day references, so hiding an account's position in the sequence means opaque or per-owner identifiers across the whole surface. A genuine duress mode is a product feature rather than a hardening detail — it needs its own threat model covering what the coerced view shows, whether the deception survives a restart or a backup restore, and what remains visible to anyone with host access, which the *Threat Model* already places out of scope. Owner isolation is unaffected either way: no account can read another account's data, and what leaks is bounded to the existence and rough number of accounts on the instance. This is not test-enforced; it is reviewed as a design decision, and revisited if Ovumcy adopts opaque public identifiers or a duress mode.
