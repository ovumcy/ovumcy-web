# Security Invariants

This file is the canonical list of the security-critical invariants the codebase enforces. Read it before changing any code that touches auth, cookies, role boundaries, or privacy data.

Every test-enforceable entry has a corresponding test or set of tests in `SECURITY.md → Test Enforcement Matrix`; policy-level entries — design rationale and deployment/CI posture that `go test` cannot verify — are reviewed by humans instead, the same carve-out the matrix states for itself, and the concern docs mark several of them "not test-enforced" in place. If you change behaviour around a test-enforced entry, the test must change in the same commit.

## Layering

- HTTP transport lives in `internal/api`, business logic in `internal/services`, persistence in `internal/db`. Do not access the database from `internal/api` directly.
- Cross-cutting concerns sit in `internal/security`, `internal/httpx`, and `internal/i18n`. Do not duplicate sealed-cookie or AEAD logic outside `internal/security` — the single HKDF + AES-256-GCM primitive (and both purpose label sets) is `SealedCipher` in `internal/security/sealed_cipher.go`.
- Templates live in `internal/templates` and use Go `html/template` auto-escape. Do not introduce `template.HTML(...)` or `template.JS(...)` with owner- or attacker-controlled input (symptom names, notes, display name, …); typed-string casts bypass contextual escaping. Embed such data as plain strings (let `html/template` escape) or via a `<script type="application/json">` island. Regression: `TestTemplateToJSONEscapesAttributeContext`.

## Role and access control

- Every state-mutating `/api/v1/*` endpoint **must** chain `handler.OwnerOnly` after `handler.AuthRequired`, even though `AuthRequired` already rejects unsupported roles via `ErrAuthUnsupportedRole`. The chaining itself is enforced against the real route table by `TestEveryAuthenticatedV1MutationChainsOwnerOnly` in `cmd/ovumcy/owner_only_route_chain_guard_test.go`, which fails when an authenticated `/api/v1` mutation never runs `handler.OwnerOnly`. The complementary matrix test `TestUnsupportedRoleRejectedAcrossEveryAuthedV1Route` in `internal/api/owner_only_coverage_regression_test.go` walks every registered route and fails when a non-public mutation accepts an unsupported-role auth cookie — it observes `AuthRequired`, the first of the two layers, and cannot see the chaining.
- The exclusion set is exactly the pre-session endpoints, which run before any session exists and therefore have no role to enforce: `POST /api/v1/users`, `POST /api/v1/sessions`, `POST /api/v1/sessions/2fa-challenge`, `POST /api/v1/password-resets`, `POST /api/v1/password-resets/redeem`. They carry no `handler.AuthRequired` either, which is how the route-table guard derives its own scope without keeping a second hand-written list. This bullet is one half of that set; the other is `preSessionV1Mutations` in `internal/api/owner_only_coverage_regression_test.go`, which the role matrix builds its public-route allowlist from, and `TestPreSessionV1MutationExclusionsMatchTheSecurityInvariantsDocument` fails when the two disagree — so a sixth exclusion cannot be added to the test literal without naming it here.
- Four page surfaces answer `GET` and yet consume a one-time value: `GET /register/welcome` spends the register-pickup nonce and mints a session, `GET /settings/calendar-feed` claims the calendar-feed reveal mark, and `GET /recovery-code` and the inline block on `GET /register` claim the recovery-code reveal mark through one shared helper. The CSRF middleware never validates a safe method, so all four apply `firstPartyRequestRefusal` (`internal/api/middleware_first_party_guard.go`) as the equivalent protection — the first two through the `requireFirstPartyRequest` middleware on the route, the recovery pair inside `claimRecoveryCodeReveal`, because `/register` is also the anonymous signup page where a cross-site inbound link is an ordinary way to arrive and only the CLAIM may be refused: a request whose Fetch Metadata headers place its initiator off this origin, give it a destination no client of these routes has, or mark it speculative takes that route's own neutral exit and consumes nothing. Requests are judged by destination rather than by being navigations, because both routes are the published `next_path` a JSON client is told to follow and such a client fetches (`Sec-Fetch-Dest: empty`); an embed (`image`, `iframe`, …) and a speculative load (`Sec-Purpose: prefetch`) are what get refused, being the shapes that spend a one-time value with nothing rendered for anybody to notice. **Each check reads its own header and fires only on a value the browser stated**, so an absent header decides nothing: a client too old for the family and one behind a proxy that strips part of it are both admitted, exactly where they landed before the guard existed. What it closes is the `SameSite=Lax` residual — Lax already withholds the cookies from a cross-site subresource load, but sends them in full on a cross-site top-level navigation. The absence is not attacker-controlled, since page script may not write a `Sec-` header. Moving the mutation to `POST` instead is a change to the response shapes published in `docs/openapi.yaml`, not to a handler. The route-mounted set is declared in `firstPartyGuardedRoutes` (`internal/api/routes.go`) and pinned against the real route table in both directions by `TestFirstPartyGuardedRoutesAreExactlyTheDeclaredSet`; the claim-mounted pair is pinned by `TestRecoveryCodeRevealRefusesAForeignRequestWithoutSpendingTheMark`, both in `internal/api/first_party_guard_regressions_test.go`.
- Only the `RoleOwner` role exists on the web product path — every account is created as `owner`, and `AuthRequired` rejects any non-owner role via `ErrAuthUnsupportedRole`. Do not introduce other roles or user-facing flows for them. An instance may host more than one independent owner (household self-hosting; single-tenant, not multi-tenant SaaS): each is the sole owner of its own data and never sees another's — enforced by the per-`user_id` scoping in the next point, not by capping the account count.
- The `users.role` column is **deliberately wider than the role model**, and that is not drift to be tidied away. Its `CHECK (role IN ('owner', 'partner'))` dates from migration 001 and still admits `'partner'` on both engines, while the product has one role and both account-creating repository methods refuse anything else (`TestUserRepositoryRefusesAnAccountWithARoleTheProductDoesNotHave`, `internal/db/user_repository_role_test.go`). Nothing reachable writes such a row: the write path refuses it and `ValidateSupportedWebUser` refuses the session. What the leftover value buys is the only way to **manufacture** the state the containment tests must prove is refused — an account row carrying a role the product does not have. Regression files construct it with a direct `UPDATE role = 'partner'` across three packages — `internal/api`, `internal/db` and `internal/services` — among them `TestUnsupportedRoleRejectedAcrossEveryAuthedV1Route` (`internal/api/owner_only_coverage_regression_test.go`), the egress-ledger stranger cases and the smoke flows. Twelve files as measured on 2026-09-04 by ``git ls-files '*_test.go' | xargs grep -l '"partner"'``; the figure is dated because nothing recomputes it, and a count without its measurement decays into a wrong one. Note the double quotes in the pattern: Go string literals carry them, and the single-quoted spelling matches only two files, which is how a reproduction recipe can disagree with the number printed beside it. Narrowing the `CHECK` would close nothing the write path has not already closed, and would delete the repository's only means of building that row — trading a guarded gap for the loss of the coverage that proves it is guarded. If the constraint is ever narrowed, those tests need a replacement way to reach the state first, and it must be one that still exercises a real persisted row.
- Every per-user query at the repository layer filters by `user_id`. There are no path parameters carrying numeric user identifiers — handlers always read the current user from `c.Locals("current_user")`.
- Input DTOs in `internal/api/input_types.go` are strictly bounded. They never expose `Role`, `AuthSessionVersion`, `MustChangePassword`, `TOTPSecret`, or `RecoveryCodeHash` to client-supplied bodies.

## Authentication and sessions

- Auth, recovery, calendar-feed-reveal, reset, OIDC state, OIDC step-up, OIDC logout bridge, OIDC link-pending, TOTP pending, TOTP setup, register pickup, and flash cookies are sealed with AES-256-GCM under an HKDF-derived key, with the cookie name (or row id, for field encryption) bound to the AEAD AAD. The AEAD core is `SealedCipher` in `internal/security/sealed_cipher.go`; `internal/api/secure_cookie_codec.go` is a thin framing layer owning only the cookie-name→AAD mapping, the `v2` version envelope (`v1` payloads are rejected on read), and base64url transport. Golden fixtures in `internal/api/secure_cookie_codec_golden_test.go` pin the stored format across refactors.
- TOTP secrets are field-encrypted under a distinct HKDF label set and AAD-bound to `users.id`. See `internal/security/field_crypto.go`; golden fixtures in `internal/security/field_crypto_golden_test.go` pin the persisted ciphertext format.
- The TOTP **enrollment seed is rendered into the enrollment page's HTML** (`{{.TOTPSecret}}` in `internal/templates/settings_2fa.html`, beside the QR code that encodes the same value) — the **second declared exception** to *no usable secret in transport*, and the narrower of the two. An authenticator app cannot be provisioned without receiving the seed, by scan or by manual entry, so the display is not removable; what makes it an exception rather than a violation is that the seed is a **not-yet-active credential**, inert until the account confirms its first code. The read-only calendar-feed capability token (*Calendar feed subscription (.ics)* below) remains the only exception for a value usable **on its own**. The exception covers this one surface, and it is the display of a freshly minted seed — never of a stored one. Regression: `TestShowTOTPSetupPage_TOTPNotEnabled_RendersQRAndSecret` in `internal/api/handlers_settings_2fa_test.go`.
- That exception holds only while all three of its bounds hold; dropping one turns the display back into a violation (`ShowTOTPSetupPage`, `internal/api/handlers_settings_2fa.go`). **Minted per visit** — every `GET /settings/2fa` mints a new key through `TOTPService.GenerateSetupKey` and renders that key, so no stored value is re-served, and an account that already has TOTP enabled gets the management view with no key generated at all. **Not persisted at display time** — the rendered seed is only sealed into `ovumcy_totp_setup` (session-scoped, five-minute payload-bound, owner-bound; next entry) and reaches `users.totp_secret`, field-encrypted and AAD-bound to the row, only through `TOTPService.EnableTOTP` after the submitted first code verifies, so an abandoned enrollment persists nothing. **Authenticated owner surface** — the page sits behind `AuthRequired`, which refuses any role but owner, and shows the account only what its own session just minted. Off that page the seed stays out of transport entirely: never in a URL, query string, JSON body, redirect, or log (`SafeLogError` masks the 32-character base32 secret). Regressions: `TestShowTOTPSetupPage_TOTPEnabled_ShowsManagementView`, `TestVerifyTOTP2FAEnrollment_InvalidCode_DoesNotEnable` in `internal/api/handlers_settings_2fa_test.go`.
- A sealed cookie that carries a per-account secret — a **one-time reveal** (the recovery code, the calendar-feed subscribe URL) or a **pending TOTP enrollment** secret — is bound to the account it was minted for, and that binding is checked against the session presenting it — the request-supplied owner id is never trusted alone. An owner id is **mandatory at seal time**, and a payload naming no owner is invalid on read rather than a check that is skipped for want of an operand: an unattributed payload reveals and enrols nothing, and is cleared. All three surfaces share one predicate, `sealedPayloadBelongsToSession` in `internal/api/sealed_cookie_transport.go`. Because the enrollment payload gained its owner id in a later release, a setup cookie minted by an earlier version fails closed and the enrollment is restarted.
- **Both one-time reveals** also carry their lifetime inside the sealed payload, and each reader verifies that against the clock before it displays anything. A cookie's `Expires` attribute is a hint to the browser, not a bound the server holds: a client that keeps the sealed value can hand it straight back on its own session, so `ovumcy_recovery_code` and `ovumcy_calendar_feed` (twenty minutes each) are refused on read once past the `expires_at` their payload carries, and a payload carrying **no** expiry — one minted before the field existed — is refused the same way rather than displayed, because an absent bound is invalid input exactly as an absent owner id is. Refusing costs the display and never the session: the reveal page already requires an authenticated one, so the account lands where it lands when the cookie is simply absent, and re-issues the secret from Settings — regenerating the recovery code, or rotating the feed token, each reachable from a surface that requires local authentication or establishes it. A refused feed reveal also logs no `settings.calendar_feed_reveal` egress event, so the audit stream counts disclosures rather than visits.
- **The server-side bound is class-wide**, not a property of those two. Every sealed cookie is bounded on the server in one of three ways: by a live expiry inside its own payload that its reader compares against the clock and refuses once past; by the opaque signed token it wraps, whose own `exp` the verifier enforces (`ovumcy_auth`, `ovumcy_reset_password`, whose sealed bytes are a JWT rather than a struct with a timestamp field); or — only where the payload names no account and carries nothing the server generated, so a replay hands the client back exactly what it already had (`ovumcy_flash`) — by nothing at all. The two exemptions are properties of the payload, never a list of cookie names, so a cookie added later is classified by what it is. `TestEverySealedCookiePayloadCarriesAServerVerifiedExpiry` derives the roster from the declared cookie specs, cross-checks it against every cookie-name constant so a spec built by a helper cannot go unseen, mints each one through its production path, rewrites the bound its payload carries into the past, re-seals it and requires the production reader to refuse it; a sealed cookie it cannot classify fails rather than being skipped.
- The **provider-logout bridge cookie** names the owner beside the session id, and the stored end-session material — the raw `id_token_hint` among it — is resolved and consumed only by that pair. This closes the last path that had no session to scope by: the bridge redirect runs after the auth cookie is gone, so the sealed payload is the only thing naming the account the hop acts for, and the lookup is never the session id on its own. An owner id is mandatory at seal time, and a payload naming none is invalid on read rather than a comparison skipped for want of an operand — it is refused and retracted, and the browser gets a local sign-out at `/login`. Because the payload gained its owner id in a later release, a bridge cookie minted by an earlier version fails closed the same way; that window is bounded by the payload's own one-minute validity.
- **One-time reveals are consumed server-side.** Clearing the reveal cookie in the response asks a browser to forget a value it was handed and binds nothing that kept it, so the cookie decides only *which* secret may be shown. Whether it still may be is a per-account mark on the `users` row — `recovery_code_revealed_at` and `calendar_feed_revealed_at` (migration 036) — claimed with a compare-and-set (`UPDATE … WHERE the column IS NULL`) before anything is rendered, in the same shape `totp_last_used_step` uses for TOTP step replay. Every reveal surface passes it: the dedicated recovery-code page, the inline post-registration block, and the calendar-feed reveal page. Replaying the original sealed value on the owner's own session therefore reveals nothing and records no second **disclosure** — the refusal is audited on the same action with `outcome="denied"`, the shape `data.export` already uses, so an operator counting disclosures counts success lines and one asking whether a spent reveal was replayed has a line to read — a concurrent second tab loses the same race, and the refusal survives a restart or a second replica because the record is in the database rather than in a process. Every UPDATE that mints a fresh secret NULLs the matching mark in the same statement, so a regenerate, reset, generate or rotate arms exactly one new reveal — the mark tracks the outstanding reveal, it never retires the surface. A refusal retracts the cookie in that response and costs the display only: the account keeps its session, lands where it lands when no cookie is presented, and re-issues the secret from Settings.
- A sealed cookie the server has just **refused is retracted in the same response**, never left in the browser. This is the standing shape of every sealed reader in the transport layer, and it matters most on the two TOTP cookies, which are session-scoped (no `expires` attribute of their own, only a payload-bound five-minute validity): an unopenable, tampered, malformed, unattributed, secret-less, foreign, or expired value used to keep being sent on every request until the browser closed, although the payload's own expiry had already made it useless. The enrollment cookie is the one whose payload is a raw TOTP secret, so an abandoned enrollment was the case worth closing. A refusal that is *not* about the cookie — a wrong six-digit code — deliberately leaves it in place, so the retry the response invites is still possible.
- Ending a session **retracts** every sealed cookie scoped to it, rather than leaving one to expire on its own: the auth cookie, the provider-logout bridge, the recovery-code and reset-password handoffs, both TOTP cookies, and the one-time calendar-feed reveal. One shared helper (`clearAuthRelatedCookies` in `internal/api/handlers_auth_token_helpers.go`) covers logout, account deletion, and the paths that reject a session outright, so a new session-scoped cookie is added in one place. This matters most where a cookie has no browser-side expiry of its own: both TOTP cookies are session-scoped and carry their TTL only inside the sealed payload, so an enrollment opened and abandoned would otherwise keep sending its raw secret at `path: "/"` for the rest of the browser session, waiting on some later request to read and refuse it — and the feed subscribe URL is a bearer capability that signing out does not revoke. Cookies whose flow completes outside a session are deliberately untouched: the OIDC one-time state and step-up cookies and the register-pickup handle are consumed by their own flow and carry their own single-use guarantee.
- A session that **ends** — sign-out, account deletion, or a server-side teardown of a session the same request had just issued (the OIDC callback whose provider-logout state cannot be stored, an abandoned register pickup) — additionally retracts the two cookies that are neither sealed nor session-scoped: `ovumcy_lang`, the year-long plaintext cache of the account's chosen interface language, and `ovumcy_tz`, the browser's own timezone (`clearSessionEndCookies`, same file). Left behind, they tell whoever opens a shared browser next that this app is used here, in which language and from which region, before anyone has authenticated. The timezone half holds only because the client stops volunteering it while signed out — the early bootstrap script is not served to an anonymous page and the request header is not attached from one — without which the next page load would put the cookie straight back. A session the server merely **refuses** — an expired or invalid cookie, an unsupported role — deliberately leaves it in place: that path is reachable by any unauthenticated request, so clearing there would be a rendering change anyone could trigger, and would cost a visitor whose session lapsed mid-use the language of the login page they are reading. An ending clears it; a refusal does not.
- The language the interface renders in has two carriers, and the **account** is the durable one: `POST /lang`, the public switcher on the login and onboarding pages, writes `users.interface_language` as well as the cookie whenever the request carries a valid owner session — through the same service call `PATCH /api/v1/users/current/interface` uses, so both surfaces share one validation and one write. Without that half, the next session issue re-wrote the cookie from the account column and silently reverted a mid-session switch. A request with no session changes only its own cookie, and the answer is the same either way — the write is invisible in the response, so the route reveals nothing about whether the cookie it was given names a live account. A language this build does not ship never reaches the account.
- A request that outlives the 60-second request budget is answered `503 request_timeout` with the handler's response discarded **in full** — status, body and headers. The key invites a retry, so a `Set-Cookie` or `Location` from a sign-in or a step-up whose work committed just after the budget expired must not ride along: the caller would act on "nothing happened" while already holding the session. `RequestDeadlineGuard` (`internal/api/middleware_request_deadline.go`) rolls the response headers back to the state they were in when it took over, which discriminates by position rather than by name — everything the composition root writes ahead of the routes (the browser-hardening headers, the CSRF cookie) survives, everything a handler added does not.
- Operations that rotate a long-lived credential (password change, password reset, recovery-code regeneration, forced operator reset, TOTP enable/disable, clear-data) must bump `users.auth_session_version` in the same atomic database update, invalidating every active auth cookie for that user. The originating device gets a freshly issued cookie inline. Changing an account's **email** through the operator CLI (`ovumcy users set-email`) bumps it for the same reason: the address is the identity both the credential path and the OIDC email match resolve an account by, so it is a posture change even though no credential is rewritten.
- **Password recovery takes two factors, not one.** `POST /api/v1/password-resets` requires the account's **current password alongside** the recovery code: the recovery code substitutes for the second factor (TOTP), never for the first. Holding the recovery code alone therefore buys nothing — before this, one captured secret minted a reset token, rewrote the password, was handed a session, and could then disable 2FA with the password it had just set, because `DELETE /api/v1/users/current/2fa` asks only for a password. The route stays open to the person it was written for: an owner whose `users.totp_secret` stopped decrypting after a `SECRET_KEY` rotation still knows the password and only lost TOTP, so gating on a TOTP **code** was rejected as a lockout. The cost is stated plainly rather than glossed — an owner who has forgotten the password and holds only a recovery code can no longer self-serve and needs the operator CLI `ovumcy reset-password <email>`, which requires shell or container access, and, because a forced reset also revokes the account's calendar feed, needs the restore fence at `CALENDAR_FEED_FENCE_PATH` to confirm before it runs — see [self-hosted.md → Calendar Feed Restore Fence](self-hosted.md#calendar-feed-restore-fence). Regressions: `TestRecoveryResetRefusesWithoutTheAccountPassword`, `TestRecoveryResetIssuesAResetTokenForPasswordAndRecoveryCode` in `internal/api/auth_recovery_reset_requires_password_regressions_test.go`.
- The second operand adds **no oracle**. Recovery stays enumeration-safe: step 1 answers `{"ok":true,"next_step":"recovery_code"}` for any syntactically valid address, and on step 2 an unregistered address, an account with `local_auth_enabled=false`, an empty stored hash, a wrong recovery code, a wrong or empty password, and an unsupported role all collapse to one `ErrRecoveryCodeNotFound` and one mapped error spec — identical status, identical body — while each books a failure on **both** attempt buckets (per-address and HMAC'd per-identity), so a `429` differentiates nothing either. Timing is equalized to match: the two credential comparisons are never short-circuited against each other — both run and only their combined result decides — and the early-return paths spend both operands' compute against fixed cost-12 placeholders (`equalizeRecoveryCodeLookupTiming`, `internal/services/auth_service.go`). Skipping the password compare after a failed code compare would cost one bcrypt comparison instead of two and time-leak which secret was right. A JSON body carrying no `password` member at all is a different question and is answered before that collapse: it is the shape this endpoint accepted before v2.0.0, so it is refused by name (`recovery reset requires the account password`) without an account being read — it names no credential, so it can reveal none, and only the JSON transport can ask it, an omitted and an empty form field being the same wire fact. Regressions: `TestRecoveryResetNamesTheV1BodyItNoLongerAccepts` in `internal/api/api_v1_declared_breaks_contract_test.go`, `TestRecoveryResetKeepsWrongPasswordIndistinguishableFromWrongRecoveryCode` in `internal/api/auth_recovery_reset_requires_password_regressions_test.go`, `TestRecoveryLookupSpendsBothCredentialComparesWithoutShortCircuit` in `internal/services/auth_service_recovery_lookup_timing_barrier_test.go`.
- Auth sessions are **absolute-expiry only by design** — TTL 7d (30d remember-me), no idle/inactivity timeout. Exposure is bounded by the absolute TTL and by instant server-side revocation: every request re-checks `auth_session_version`, so any credential/posture change invalidates the cookie immediately. The absence of an idle timeout is a deliberate trade-off for a personal tracker, not an omission.
- Auth session tokens use `jwt.SigningMethodHS256`. The parser explicitly rejects non-HMAC and `none` algorithms.
- The OIDC sign-in flow is Authorization Code + PKCE (S256). `response_mode=form_post` is the default; `OIDC_RESPONSE_MODE=query` is an opt-in for query-only providers (better-auth, Dex, Pocket ID <2.7), where the provider returns the code in the callback URL — inert without the PKCE verifier, which never leaves the sealed HttpOnly state cookie, so a query-mode code is not a *no usable secret in transport* violation. The verifier and `state`/`nonce` live in a single sealed cookie; the callback exempts CSRF (justified by state/nonce/PKCE replacing it) — `POST` in form_post mode, additionally `GET` in query mode (a safe method the middleware never validates). Callback parameters (`state`/`code`/`error`) are read from a single source keyed by mode — the URL query in query mode, the POST body in form_post mode — never both. The ID-token allowlist is asymmetric-only (`RS*`, `ES*`, `PS*`, `EdDSA`); `HS*` and `none` are refused even if the provider advertises them. The discovery-supplied `jwks_uri` is origin-pinned to the configured issuer; a cross-origin `jwks_uri` is rejected before any verifier is built.
- Behind a trusted proxy, the edge rate limiters key on the rightmost untrusted `X-Forwarded-For` hop (relative to `TRUSTED_PROXIES`), so a client-spoofed XFF prefix cannot defeat per-IP limits. `PROXY_HEADER` controls fiber's `c.IP()`, which backs only the secondary per-client auth buckets.
- An edge rate limiter scoped to a single endpoint decides whether a request is its own by comparing the path in the **router's own normalization** — case folded, trailing slashes stripped — never as raw bytes. Fiber hands a handler the untouched path off the wire while matching routes against a normalized copy, so a raw-byte comparison exempts `POST /LANG` and `POST /lang/` from the cap on `POST /lang` while both still reach the language handler. The comparison stays exact rather than prefix-wide, so a deeper sibling path (`POST /api/v1/sessions/2fa-challenge`) does not spend the endpoint's budget.
- Rate-limit and `AttemptLimiter` state is **in-memory, process-local by design** — correct only under the single-instance self-hosted contract. It is not shared across replicas and resets on restart; horizontal scaling would multiply per-IP budgets and requires an external shared store. Do not rely on limiter state across processes.

## Privacy and PII

- Recovery codes, TOTP secrets, submitted codes, rate-limit identity material, plaintext passwords, and email addresses must not appear in any log output. `SafeRequestLogPath` (in `internal/api/request_logging.go`) masks `:email`, `:id`, `:date`, and opaque tokens in the request path; the companion `SafeLogError` masks emails, opaque tokens, recovery codes and submitted one-time codes in the request log's error field. Both run before any audit emission. `SafeLogError` recognizes secrets by **shape, not only by length**: the opaque-token rule needs 24 characters, which the 48-character calendar-feed token and the 32-character base32 TOTP secret clear but a 19-character recovery code and a 6-digit submitted code do not, so those two carry their own rules (`OVUM`-prefixed grouped alphanumerics, and a standalone run of exactly six digits). The length floor is deliberately not lowered instead: a low generic floor would redact dates, status codes, route templates and ordinary identifiers, and the request log's error field is the operator's only diagnostic signal for a failed request.
- The off-by-default audit stream (`AUDIT_LOG_ENABLED=true`) tags health actions with **two disjoint domains**, so one filter cannot answer for the other: `domain="health_data"` marks an action that **changed or destroyed** tracked data, `domain="health_egress"` one that **carried it out** of the instance (the CSV, JSON and summary exports) or **revealed a secret granting standing access** to it (the `.ics` subscribe URL, a recovery code). Both carry a fixed `target` designator, never an identifier or submitted text, and an egress line records the *fact* of the disclosure only — no export payload, subscribe URL, feed token, or recovery code ever enters a log line. The audited moment is the one where the data or the secret reaches a person; polling of the calendar feed is deliberately not audited (see *Calendar-feed polling is not audited* in `docs/security/known-disclosures.md`). Field reference: `docs/security/logging.md`; see the matrix's *Logging Policy* rows.
- Auth and settings flash banners must come from sealed cookies or session state, never from URL query parameters. Do not introduce `?error=`, `?status=`, or `?email=` notification sources.
- The same rule holds for a query parameter the app never produced: nothing the caller put in the URL is echoed back into a rendered page or into an outgoing URL. `SanitizeCurrentPathQuery` (in `internal/services/redirect_policy.go`) filters the address the shared layout renders on every page — the language switcher's `next` field and the footer `/privacy?back=…` link — and, through `SanitizeBackNavigationValue`, the privacy page's own back link. The filter is over **names and value shapes together**: the allowlisted names are the parameters the page handlers actually read (`month`, `day`, `selected`, `edit`, `step`, `back`), and each retained value must match what its own consumer accepts — `month` the `2006-01` layout, `day`/`selected` the `2006-01-02` layout, `edit` `ParseBoolLike`'s truthy set, `step` the 1..2 `ResolveOnboardingStep` can reach. Names alone are not a filter: `?step=victim@example.com` renders exactly what `?email=` would. The fragment is dropped first (it lives in the path half, and a caller-controlled `back` value can carry one), the survivors are emitted in a deterministic order, and a query the parser rejects fails closed to the bare path. `back` is filtered by the same policy exactly one level down and must additionally be a redirect-safe path built from the characters this app's routes use, so `/victim@example.com` is refused as a back target. Add a parameter to the allowlist only together with the handler that reads it, and give it a shape derived from that handler rather than an invented one. Regression: `TestSanitizeCurrentPathQuery`, `TestBuildPrivacyBackNavigationAppliesTheWholeBackValuePolicy`, `TestPublicPageDropsAHostileValueUnderAnAllowlistedKey`.
- Public registration (`POST /api/v1/users`) requires explicit consent — the `consent` field must be truthy (`true`/`1`/`yes`/`on`). The browser checkbox lives on `/register`; the backend rejects requests without consent with `auth.error.consent_required`.
- Health data is **owner-only**. The `clear-data` and `delete-account` flows require fresh re-authentication — the current local password, or a fresh purpose-bound OIDC step-up for an account that has no local password — and bump `auth_session_version`. An account that has a local password is refused the step-up route, so it never substitutes for a password gate that applies.
- Restoring a JSON export (`POST /api/v1/imports/json`) is **additive and owner-scoped**: it only creates calendar days the account does not already have, never overwrites or deletes existing days, and re-validates every field of the (untrusted) file server-side. Because it destroys nothing, it needs no re-authentication at all — but it is state-mutating and therefore owner-only and CSRF-protected.
- Outbound webhook reminders are **owner-scoped egress**: the request-free notify pass delivers each owner's reminder only to that owner's decrypted URL, so one owner's predicted health data never reaches another owner's endpoint. The rest of that subsystem's invariants have their own section below.

## Webhook notifications (outbound egress)

- The endpoint is **owner-controlled**, so the request envelope is hardened rather than the destination blanket-blocked: bounded timeout, no keep-alives, zero redirects, `http`/`https` only, a size-capped response read, and an explicit cap on the response header block (which is read before the body cap can apply and otherwise takes Go's 10 MiB default). A saved endpoint must name a host and, when it carries one, an in-range port — re-checked before delivery, since save-time validation never revisits a stored row.
- An operator can additionally opt into an **off-by-default private-address block** (`WEBHOOK_BLOCK_PRIVATE_ADDRESSES`). When on, the destination host is resolved and refused if **any** resolved address is private/loopback/link-local, including ranges Go's own helpers omit: RFC 6598 CGNAT, `0.0.0.0/8`, `fec0::/10`, and the RFC 8215 local-use NAT64 block. It also refuses every remaining address the IANA special-purpose registries record as **not globally reachable** — benchmarking, IETF protocol assignments, documentation, reserved and multicast space among them. The prefixes those registries record as globally reachable stay deliverable — AS112, AMT and the `2001:1::1-3` anycast addresses — with one deliberate exception: the PCP and TURN anycast addresses `192.0.0.9` and `192.0.0.10` are refused together with the `192.0.0.0/24` protocol-assignment block that contains them, since an egress gate errs toward refusal and no owner endpoint lives there.
- That block also covers **every IPv6 transition form that embeds an IPv4 destination** — NAT64, 6to4, Teredo, IPv4-compatible, IPv4-translated. Each is classified by the address it wraps rather than by its wrapper, because that is where it routes, so a wrapped private address is refused while a wrapped public one stays allowed.
- The connection is then dialed to the **validated IP** rather than re-resolved, so a rebinding record cannot slip a private target past the check between validation and dial.
- Delivery logs and returns the destination **host only** — never the full URL, path, query, or userinfo, which may embed a notification token — and every payload carries the medical-safety disclaimer with no secret in the body.
- Owners configure the webhook from the settings page, where the URL is a **write-only secret**: encrypted at rest and never rendered back into the page once stored (only a configured/not-configured status plus at most the hostname is shown), so a token embedded in the URL never re-enters transport. A blank URL on save leaves the stored endpoint unchanged; a distinct remove control clears it.
- The operator CLI holds the same line on both halves. `ovumcy notify` prints counts, owner ids and destination hosts but **no reminder type and no estimated date** unless the operator explicitly asks with `--show-health-details`, so a scheduled pass redirected into a log records no prediction about an identified owner. `ovumcy webhook set` accepts the endpoint from exactly one out-of-band source — supplying both `OVUMCY_WEBHOOK_URL` and `--url-stdin` is refused rather than silently resolved, so a stale ambient export cannot arm an owner's reminders at an endpoint nobody typed.
- A **revocation survives a pass already in flight**. The reminder pass reads every owner's configuration once and delivers minutes later, so an owner who disables delivery, replaces or removes the endpoint, changes the shared reminder lead window, or clears all data must be able to rely on the confirmation they were shown. Each of those writes advances a per-owner monotonic revocation epoch in the same statement, and the claim the pass takes immediately before the request pins the epoch its own snapshot carried, so a pass holding a configuration the owner has revoked delivers nothing — the erasure case included, where the wipe would otherwise re-open the pass's "nothing sent yet" path. The stated limit is that a request already on the wire cannot be recalled: the guarantee is that no new request begins under a revoked configuration.
- See the matrix's *Webhook Notifications (outbound egress)* rows.

## Calendar feed subscription (.ics)

- The read-only `.ics` feed (`GET /calendar/feed/:token.ics`) is authenticated by a **bearer capability token in the URL path** — the single sanctioned exception to *No usable secret in transport* for a value usable **on its own** (a usable value in a URL), because calendar clients send no cookie or auth header. It is a capability token, **not an auth credential**: it authorizes only a read-only `.ics` of that one owner's own predicted cycle events, never account access, settings, or mutation, and it never touches `auth_session_version`. The TOTP enrollment seed, declared under *Authentication and sessions* above, is the only other exception and a narrower one: it is inert until the account confirms its first code.
- The token is **selector + verifier**: the 16-char selector (~80 bits) is a non-secret plaintext UNIQUE-indexed lookup id; the 32-char verifier (~160 bits) is secret and **never stored in plaintext** — the row holds a keyed MAC of it (`HMAC-SHA256` over `(selector, verifier)` under a `SECRET_KEY`-derived HKDF key) plus a bcrypt hash kept for rollback. The full subscribe URL is shown to the owner exactly once at generation (like a recovery code) and is never persisted or re-rendered afterward.
- **The MAC, not bcrypt, is what verification compares.** A 160-bit random verifier is not guessable with or without a work factor, so bcrypt bought nothing here while costing ~265 ms of CPU per request on a cookieless unauthenticated endpoint. The MAC is keyed rather than a bare digest so a database leak alone still does not permit offline verifier guessing. A stored MAC that does not match is a **hard refusal** — never re-checked against bcrypt — so rotating `SECRET_KEY` disarms armed feeds and each owner re-generates the subscribe URL from settings, the same class of consequence already documented for `users.totp_secret` and `users.webhook_url`.
- A row minted **before migration 032** carries no MAC (it cannot be derived from a hash) and still verifies through bcrypt. The MAC is written in during the first request that presents the correct token, under a compare-and-set scoped to that owner **and** that selector, so a rotation racing the write can never pair an old token's MAC with a new token's hash; a failed write never withholds a feed whose token verified. A rotation cannot be missed through this bcrypt window: a boot-time sentinel keeps a `SECRET_KEY`-derived **key epoch** in `app_state` and, on the first start under a changed key (or a bumped feed-MAC label set), disarms every armed no-MAC row before the listener accepts a request — so the backfill can never re-arm a leaked URL under the new key. The first start after upgrading, which finds no stored epoch at all, disarms those rows as well rather than recording them as its baseline: nothing there says which key minted them, and adopting them would leave the backfill free to re-arm one under today's key. A new installation reaches the same branch holding no such row, so it disarms nothing.
- A **backup restore** cannot revive a revoked feed either, and it needs its own mechanism: the key epoch above is stored in `app_state`, so a restore returns it together with the feed columns and the two can never disagree. The **restore fence** keeps its second half outside the database — a file at `CALENDAR_FEED_FENCE_PATH`, mounted from a location no database backup captures — and every write that arms, rotates or removes a feed advances both halves together. A restored database therefore carries a marker older than the file's; the boot pass reads that disagreement as "this is not the database this instance last wrote" and disarms every armed row, MAC or not, before the listener accepts a request. Nothing here depends on the operator remembering a step, which is the point: containment has to survive a restore, not be re-applied by hand after one. Where no fence is available — no mount, no variable — the pass fails closed instead, disarming every armed feed on each start and saying so in the startup log. It also **stamps the database as having started unanchored**, because that period is a hole of its own: with no half outside the database, a revocation made then is recorded in exactly one place, and a backup taken then carries neither a fence token nor anything the file half could contradict. Both halves empty is otherwise the signature of a first boot, so without the stamp the first start after an operator finally mounts a fence would adopt the rows in front of it and hand back a subscribe URL its owner had revoked. With it, that start disarms every armed feed instead and then erases the stamp, so an ordinary restart is never turned into a disarm — the stamp is read **only** where both halves are empty, never as an override of two halves that agree. The operator CLI's own feed-revoking commands — `ovumcy users delete`, a forced `ovumcy reset-password` — refuse outright on such an instance instead of completing, since each must advance that same fence immediately before the write that would revoke a feed (`internal/cli/repositories.go`).
- Verification gives **no oracle**: a malformed token, an unknown selector, a wrong verifier, and a disabled feed all return an identical `404` — the fixed status-text body `Not Found`, carrying nothing cause-specific and no `Set-Cookie` — so the answer distinguishes none of the four causes. The selector-miss path is timing-equalized by re-executing the real verification against a placeholder MAC, so the equalization tracks whatever primitive verification uses rather than hardcoding one — a dummy pinned to bcrypt while verification moved to a MAC would have kept the full CPU cost on every random token. The selector is compared with `subtle.ConstantTimeCompare` and the verifier with the keyed-MAC compare, combined with a bitwise AND so the verifier cost is always paid. **One transitional exception:** a not-yet-migrated pre-032 row still pays bcrypt, so its wrong-verifier latency is distinguishable from a selector miss until its first successful poll. Reaching that signal requires already holding a valid 80-bit selector — a leaked subscribe URL carries both halves, so there is no realistic path to the selector alone — and the feed's per-IP budget caps the attempt rate. That `Set-Cookie` absence is not particular to the 404 answer above: on GET or HEAD, on any spelling of the URL the router treats as the same route (case-folded, trailing slash alike — the shared predicate is `api.IsCalendarFeedRequest`, compared on fiber's own normalized path rather than the raw wire path; see its own godoc for the exact route-shape rule), the route is excluded from both app-wide middlewares that would otherwise write a cookie on any safe method lacking a matching one — the CSRF middleware's own token-issuance side effect and `LanguageMiddleware`'s timezone-cookie persistence, both mounted in `cmd/ovumcy/server.go` ahead of the route — so no outcome (200, 404, or the rate limiter's own 429, which the same predicate also scopes) ever carries one. Neither exclusion is a CSRF *validation* exemption: GET and HEAD are safe methods neither middleware validates in the first place, only mints a cookie for; see *CSRF and CORS* below.
- The subscribe URL is a **write-only secret**. Generate and rotate seal the full URL into a one-time AEAD cookie (`ovumcy_calendar_feed`) and redirect to a dedicated reveal page (`GET /settings/calendar-feed`) that claims the owner's consumption mark, clears the cookie, and renders the URL exactly once; on any later settings load, refresh, redirect, JSON response, query string, or log it is **never** rendered again. JSON clients receive only a `next_path` to the reveal page, never the URL or token. "Exactly once" rests on the mark rather than on the cleared cookie — see *One-time reveals are consumed server-side* below.
- The token is **revocable and rotatable**: `DELETE /api/v1/users/current/calendar-feed` clears every feed column (the feed then `404`s) and `POST …/calendar-feed/rotate` mints a new selector + MAC + hash so the previous URL dies immediately. Because the token is a long-lived bearer capability that outlives login sessions, it is **force-cleared in the same atomic `auth_session_version` bump** on password reset via recovery code, owner-initiated recovery-code re-generation (the `RegenerateRecoveryCode` path — the *first* recovery code minted during initial local-password setup is deliberately **not** a clear event: it is not a compromise, and the owner keeps the manual rotate control), forced operator reset, and clear-data; a routine authenticated password change deliberately **keeps** it (the owner rotates manually).
- The feed's **not-found path answers outside the app-wide error envelope**, deliberately: `text/calendar` on success, and otherwise the fixed status-text `404` body `Not Found` for every unknown, malformed or revoked token. The envelope negotiates its shape from the caller's `Accept`/`HX-Request` headers and carries localized copy, so on a public cookieless route with no UI it would let an anonymous caller choose the shape of the answer, and the fixed body is one thing that has to stay identical across all four not-found causes. This is the same carve-out `/healthz` and `/readyz` hold for the same reason; the three of them are the whole set, named in `docs/openapi.yaml` and swept by `TestEveryRejectionOutsideTheDeclaredExemptionsCarriesTheEnvelope`. The per-IP `429` is the one refusal that does take the application's shared rate-limit answer: the feed has no page behind it, so its limiter refuses through the same negotiated path as every other limiter — `docs/security/auth-policy-and-rate-limits.md → Rate Limits` owns that shape — and the exemption covers the not-found answer, never the route wholesale.
- The feed is hardened in transport: `SafeRequestLogPath` emits the route template `/calendar/feed/:token.ics` verbatim and the raw-path fallback masks an `<opaque-token>.ics` segment, so the token never reaches a log; the endpoint is per-IP rate-limited and served `X-Robots-Tag: noindex`, `Cache-Control: private`. Every `.ics` event carries the medical-safety disclaimer (it is a prediction surface) and a neutral, contentless title, so no cycle-phase detail leaks to anyone who can see the owner's calendar. See the matrix's *Calendar Feed Subscription (.ics)* rows.

## CSRF and CORS

- CSRF middleware is global on every state-changing request. The single **validation** exemption is the OIDC callback `/auth/oidc/callback` — `POST` in form_post mode and, under `OIDC_RESPONSE_MODE=query`, additionally `GET` (a safe method the middleware never validates) — where the OIDC provider cannot present our token and the sealed `state`/`nonce` cover replay protection. The middleware's `Next` predicate carries one further, unrelated clause: a GET or HEAD matching the calendar feed's own route shape (`api.IsCalendarFeedRequest`), which stops it from minting and setting its own cookie on a safe method it was never going to validate (*Calendar feed subscription* above). That is not a second validation exemption, and the mutating-route count stays exactly one — see the matrix's *Cookies* rows.
- A valid token is not the only requirement: the middleware also matches the request's `Origin` (falling back to `Referer` when the app is served over HTTPS) against the scheme and host the app itself observes. A mismatched `Origin` is refused in any posture; a *missing* one is refused only over HTTPS. **Operator consequence:** behind an HTTPS terminator the app must be told to trust it (`TRUST_PROXY_ENABLED=true` with the proxy listed in `TRUSTED_PROXIES`), otherwise the app observes plain `http`, disagrees with the browser's `https://…` `Origin`, and answers `403` to every form submission. See the matrix rows under *Session and Cookie Security*.
- Global CORS is **disabled**. Do not enable `Access-Control-Allow-Origin: *`.

## Cryptographic baseline

- AEAD: AES-256-GCM (sealed cookies, field encryption), implemented once in `internal/security/sealed_cipher.go`. Key derivation: HKDF-SHA256 with versioned, purpose-specific salt and info labels; the two purposes derive distinct keys, so cross-purpose opens fail (see `SECURITY.md → SECRET_KEY Usage Map`).
- Randomness: `crypto/rand` for nonces, session IDs, OIDC state/nonce, PKCE verifiers, recovery codes. **Never `math/rand` for security-sensitive values.**
- Comparisons: `crypto/subtle.ConstantTimeCompare` for OIDC state, recovery-code hashes (via `bcrypt.CompareHashAndPassword`), TOTP code validation, calendar-feed verifier MACs, and password-state fingerprints.
- Passwords are bcrypt cost 12 (a successful login re-hashes any older, lower-cost hash in place without invalidating the session). Minimum length 8 with at least one uppercase, one lowercase, and one digit.

## Content Security Policy

- The CSP shipped from `cmd/ovumcy/server.go` is `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self'; manifest-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'; worker-src 'none'`. Do not introduce `unsafe-inline`, `unsafe-eval`, `data:` outside `img-src`, or `*` in any directive.
- Templates must not contain inline `<script>` blocks, inline event handlers (`onclick=`, `onload=`, …), inline style attributes, or `javascript:` URLs.
- The same `securityHeadersMiddleware` (`cmd/ovumcy/server.go`) sets these companion headers on every response: `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (geolocation/camera/microphone/payment/usb/… all `()`), `Cross-Origin-Opener-Policy: same-origin`, `X-Frame-Options: DENY`, and `Strict-Transport-Security` (controlled by `HSTS_ENABLED`, which defaults to the `COOKIE_SECURE` value; set `HSTS_ENABLED=false` to run secure cookies without the 1-year HTTPS pin).

## Medical safety

- Health predictions are estimates, never fact. Every owner-facing prediction surface — dashboard, stats, and calendar — renders a persistent "estimates, not medical advice or a method of contraception" disclaimer alongside the estimate qualifiers.
- The wording lives in exactly one catalogue entry (`medical.disclaimer`) that every one of those surfaces references, together with the two settings sections that ship predicted dates off the instance — webhook reminders and the calendar feed — and the webhook payload and `.ics` feed themselves. Consolidating the TEXT never consolidates the REQUIREMENT: the number of surfaces that show the disclaimer is itself the invariant.
- A template refactor cannot silently drop it: backend regressions assert the disclaimer on each surface via a stable `data-*` hook plus the exact safety string (`TestDashboardRendersPredictionDisclaimer`, `TestStatsRendersPredictionDisclaimer`, `TestCalendarRendersPredictionDisclaimer`, `TestSettingsEgressSurfacesRenderPredictionDisclaimer`). This is the one place backend tests deliberately pin localized copy, because the wording itself is the invariant.
- **Display confidence follows data confidence: suppression is the floor.** Where the only source is a configuration default or a projection past the account's own reference range, the window is withheld rather than qualified — unpredictable-cycle mode, a pregnancy pause, an overdue cycle, and for the fertility half an account with no completed cycle. Every surface asks one predicate per half rather than rebuilding the rule, so a new signal is added once. See the matrix's *Medical Safety Disclaimer* rows.
- **Withholding travels with the data, on the API as on the pages.** Every surface that publishes a projection does so through one adapter, which clears the dates the verdict refuses before anything can render or send them — so a template, a partial or a JSON view that forgets the gate has nothing to publish rather than a suppressed estimate. `GET /api/v1/stats/overview` returns an explicit payload, not the internal statistics object: suppressed dates are `null`, the response names the reason in a stable machine-readable form (`unpredictable_cycle`, `pregnancy_pause`, `cycle_overdue`, `awaiting_first_cycle`), and carries the medical-safety disclaimer with its catalogue key. Recorded history is published in every state — it is fact, not projection.

## Deployment

- The runtime container is `FROM scratch`, runs as `USER 10001:10001`, mounts a read-only filesystem with `tmpfs` for `/tmp`, drops all capabilities, and disables new privileges. Health checks use the in-process `ovumcy healthcheck` subcommand. Do not add shell, package manager, or Node.js / Playwright into the runtime image.
- The two probes are public and unauthenticated by nature, so neither may become a reconnaissance surface. `/healthz` reports liveness and never touches the database. `/readyz` performs exactly one trivial storage query and answers `200` or `503` with a fixed, non-revealing body — never a driver name, database path, or error string. Do not extend either probe with diagnostic detail, and do not repoint the container `HEALTHCHECK` at `/readyz`: a storage blip must not restart the container.
- `SECRET_KEY` (or the file behind `SECRET_KEY_FILE`) is the single application-wide secret. It must be at least 32 bytes of cryptographically secure randomness; placeholder values are refused at startup. Store it separately from data backups (`docs/gdpr.md → SECRET_KEY Management`).
- Default `HOST_BIND_ADDRESS` is `127.0.0.1`; public deployments must use the reverse-proxy compose stacks where only the proxy publishes host ports.
- Release and CI images are built from a clean Git checkout (or `git archive` tarball), never from a developer working tree: the Docker build context must contain only tracked files. The runtime image additionally copies an explicit allowlist (`cmd`, `internal`, `migrations`, `web`), so local-only tooling and untracked working files can never reach a build performed by a remote builder or CI.

## CI

- All GitHub Actions are pinned to immutable commit SHAs. Workflow `permissions:` are minimal; SARIF and Codecov uploads are gated by a fork-PR check.
- Security scans (`gosec`, Trivy filesystem, Trivy image, CycloneDX SBOM) and CodeQL run in dedicated workflows. They target `./cmd/...` and `./internal/...` plus the runtime image; they intentionally exclude `.tmp/` and other ephemeral lab directories.
- The container image is published only after the same commit's own checks have passed. The publish is the last job of the CI workflow, behind `test`, `race`, `e2e`, `e2e-postgres-smoke` and `image-smoke`, and it scans the exact image it is about to push (Trivy, fixed HIGH/CRITICAL) before the first byte reaches the registry. `ghcr.io/ovumcy/ovumcy-web:latest` therefore trails a push to `main` by a full CI run and stays on the previous commit whenever a check fails. Release tags publish from their own tag push through the same job, which is also what keeps the keyless-signing identity in *Verifying Release Authenticity* stable for both.
- **A public tag exists only once the digest under it is signed.** The image is pushed **by digest, under no tag at all**; the cosign signature and the SLSA provenance attestation are made against that digest and then read back from the registry; only then are the tags written, from the manifest bytes that already hash to the signed digest, so an alias cannot come to point anywhere else; and each tag is finally checked to be anonymously pullable and to resolve to that same digest. A failure before the tags are written leaves an untagged manifest and no public alias at all; one during the write can leave the aliases written before it, and every alias that exists points at the signed digest. That last clause is the guarantee, and it holds in both cases. The ordering is the invariant, not a description of the happy path: a red workflow retracts nothing, and nothing deletes a tag that already resolves — so a publish that signed after tagging would leave an unsigned release standing behind a failed run. Enforced by `scripts/publishorder`.
- The repo-root `osv-scanner.toml` is live configuration, not a leftover: the OpenSSF Scorecard workflow's Vulnerabilities check runs the osv-scanner library over the checked-out tree, and osv-scanner resolves its config next to the scanned manifest — for the repo-root `go.mod`, that file. It suppresses only findings that are provably outside the build graph, each with a written reason; reachability itself is still gated by `govulncheck`, which is never suppressed.
- **One documented exception to digest-pinning:** `.clusterfuzzlite/Dockerfile`'s `FROM gcr.io/oss-fuzz-base/base-builder-go` is intentionally not digest-pinned. It is an ephemeral fuzzer-build sandbox — never a shipped or scanned runtime image — and ClusterFuzzLite requires the rolling tag so the bundled Go/clang toolchain stays compatible with `go-118-fuzz-build`; a stale pinned digest would eventually break fuzzer builds rather than improve safety. The `go-118-fuzz-build` Go module it installs (no tagged releases) is pinned to a pseudo-version in `.clusterfuzzlite/build.sh`.
